## 1. 双仓关系

| 仓                            | 职责                                       |
| ----------------------------- | ------------------------------------------ |
| `teaching-quality-enablement` | 标准、方法、愿景与 MVP 业务边界、带教路径  |
| `lesson-review-ai`（本仓）    | 流水线代码、提示词版本、运行配置、报告模板 |

口径冲突时：**以上游业务文档为准**，并回改本仓摘要与 `prompts/`，不要在本仓静默发明新标准。

---

## 2. 分支与里程碑 PR

| 分支                          | 用途                                         |
| ----------------------------- | -------------------------------------------- |
| `main`                        | 可演示、文档与代码一致；建议开启 PR 合入保护 |
| `docs/m0-...` / `feat/m1-...` | **按里程碑**开分支，多次提交后开**一个 PR**  |
| `fix/...`                     | 缺陷修复（可独立小 PR）                      |

**不采用「一 Issue 一分支一 PR」**（过碎）。Issue 仍细拆用于跟踪与验收；合入以里程碑为单位，例如：

| 建议 PR 单元 | 内容                                    |
| ------------ | --------------------------------------- |
| PR-M0a       | 文档（可按类多次 commit）               |
| PR-M0b       | Markdown / 编辑器 / uv 相关工具链与说明 |
| PR-M1        | 单视频竖切可演示                        |
| PR-M2        | 模块模式                                |
| PR-M3        | 工程化（按需）                          |

## 3. 提交与合入

- **提交信息**：`feat(scope): 原因` / `docs(scope): 原因` / `fix(scope): 原因` / `chore(scope): 原因`。
- 改 Markdown 后跑 `npm run format` 与 `npm run lint:md`（中英文空格依赖 Prettier + prettier-plugin-zh）。
- **合入门禁（当前）**：维护者确认口径、隐私与文档对齐；无确认不 push / 不合入。
- **合入门禁（工程化后）**：CI 绿 + 维护者确认（`prompts/` 变更必须附课例对比说明）。
- 文档宜**分类对齐后再分批提交**；授权语以其当场约定为准。
- public 仓提交前自检：无维护者真名、无机构/品牌名。

### PR 检查清单（建议写入 PR 模板）

- [ ] 关联相关 Issue（可多个）
- [ ] 仍落在 MVP 范围内（见 [PRD](../01-product/001_prd_课评教练MVP产品说明.md)）
- [ ] 未提交媒体、密钥、真实课例
- [ ] 无维护者真名、无机构/品牌名（public 仓）
- [ ] 若改 `prompts/`：已用脱敏样例对比报告
- [ ] Markdown：`npm run format:check` 与 `npm run lint:md` 已通过
- [ ] 若改用户可见行为：已更新 `docs/01-product` 或 CLI 契约
- [ ] 本地运行或校验命令已写在 PR 描述中

## 4. AI 可以 / 不可以

| 可以                           | 不可以                                    |
| ------------------------------ | ----------------------------------------- |
| 实现与重构流水线、提示词、脚本 | 未经确认把真实学员/教师隐私写入文档或提交 |
| 在确认后协助 git / PR          | 擅自 `push --force` 到 main；跳过 hooks   |
| 引用上游标准并注明路径         | 编造「组织已规定」的考核分数或否决项      |
| 用脱敏样例调试                 | 下载或提交大型版权课包进 Git              |

## 6. 文档与代码双轨

| 变更类型              | 先更新文档？                   |
| --------------------- | ------------------------------ |
| 新产品行为 / CLI 参数 | 先改 `01-product`，再实现      |
| 技术栈替换            | 新 ADR + `002_tech-stack`      |
| 仅重构、行为不变      | 可不改产品文档                 |
| Issue / 里程碑调整    | 改 `03-delivery/001_issue-map` |

## 7. 自检清单

- [ ] 本次改动是否仍落在 MVP 内？
- [ ] 报告语气是否对事不对人、是否区分合格线/水平线？
- [ ] 是否误把媒体、密钥、真实课例提交进 Git？
- [ ] 口径是否与上游冲突？冲突时是否以上游为准并计划回改？
- [ ] 文档与对话是否避免电报体、中英文是否保留空格？
