# ADR-0006：实操课（lab）三条套路与课型推断

- **Status**：Accepted
- **Date**：2026-07-25
- **Relates to**：报告契约课型字段；ADR-0005（共屏 / 待回放）；不替代 Pass A 假阳性闸门

## Context

维护者用「Python 解释器安装」实操样例对照后发现：

1. 标题含「安装」仍被推断为 `principle`，结构/提纲/教练按原理课评价。
2. 工具用抽象「why→what→how→verify」夸奖递进，与实操规范套路不符。
3. 实操规范要求（**课型无关**，不限于 Python CLI）：
   - **L1 推荐路径**：**作用 → 实操 → 验证 → 总结注意事项 → 扩展**（注意事项不要整段前置到实操前；官网等扩展后置）；
   - **L2**：最短主线先闭环，备选源 / 备选工具后置（官网仅当它不是主线时才后置）；
   - **L3**：一条默认验证路径；并列的第二种验证方式为扩展；主线分步确认不算多验证。

同一套 L1–L3 须能覆盖解释器安装、MySQL 安装、虚拟机安装等场景。

## Options considered

| 选项                          | 优点             | 缺点                           |
| ----------------------------- | ---------------- | ------------------------------ |
| 仅靠 `--lesson-type lab`      | 实现零成本       | 易漏标，样例已证               |
| 加强文件名推断 + lab 专用检查 | 对准误判与假夸奖 | 需提示词分支与文档同步         |
| 新建 Pass A 类别 `lab_flow`   | 机器可读         | 与结构职责重叠；本阶段可不强制 |

## Decision

1. **推断**：标题/文件名含安装、配置、环境、部署、跟做等 → 默认 `lab`（仍可用 CLI 覆盖）。多信号冲突时**实操 / 安装类优先于**原理类。
2. **`lesson_type=lab` 时**：structure / teaching_outline / coach 必须按 **L1 / L2 / L3** 自检与选题；禁止把「并列多验证」「主线未完就展开备选扩展」写成优点。
3. **Top3 权重（lab）**：在原有准确性/讲清度之后，优先 **L1/L2/L3**，再普通小闭环/深度提问。
4. **本阶段**：L1–L3 以提示词 + 结构自检为主；不强制新增 Pass A 枚举（有摘句的验证踩坑仍可用既有 `clarity`/`case`）。
5. **code 课型**：待代码类样例后再定，不在本 ADR 展开。

字段与验收以 [报告契约 v0.7.1](../../01-product/003_report-contract_报告结构与验收.md) §10 为准。

## Consequences

### 正面

- 实操课评价与带教套路对齐，减少「评错课型」。
- 验证单路径、主线优先可进入合格线候选（仍须摘句）；GUI / 服务状态类验证不被 CLI 措辞误伤。

### 负面

- 推断启发式仍可能漏/误；弱标题须 CLI 指定。
- structure/coach 提示词分支变长。

### 相关

- 报告契约 §10、CLI 契约 `--lesson-type` / 推断说明
- 提示词（确认后改）：`structure_single.md`、`teaching_outline.md`、`coach_feedback.md`、`knowledge_cases.md`（可选）
- 实现：`lesson_type.infer_lesson_type`
