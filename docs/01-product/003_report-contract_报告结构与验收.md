- **关联 ADR**：
  - `docs/02-architecture/adr/0004_two-pass-knowledge-review.md`（两段式与假阳性闸门）
  - `docs/02-architecture/adr/0005_clarity-and-playback-boundary.md`（讲清度 / 待回放 / 表达噪声）

## 1. 报告原则

1. **先结论摘要**，再证据与改法。
2. **事实 / 判断 / 建议**分开写，避免混成一句定论。
3. **合格线**（必须改）与 **水平线**（锦上添花）分栏或分节；另设 **待核实**（默认不进 Top3 必改）与 **待回放确认**（转写无法判定，见 §4.1）。
4. 语气遵守三不三要；**对事不对人**；禁止公开羞辱式表述。
5. 证据尽量引用**纠错后逐字稿摘句**（可带大致时间段），不编造未出现的内容。
6. **假阳性优先于召回**：无摘句不得判「必须改」的知识 / 案例 / 讲清度问题；标题锚点不是讲义全文。禁止用百科「应讲清单」扩大指控。
7. **优先改进 Top 3** 选题权重：**知识准确性 > 讲清度（clarity）≥ 案例恰当性 > 结构与递进 > 表达与沟通**。
8. **结构缺口不得压过本段教学目标未讲清**：例如「开场承诺三部分、本段只上一部分」可以写，但若 Pass A 已有高置信 `clarity` / `accuracy` `issue`，后者优先进入 Top3。
9. **表达噪声闸门**：口头禅、边打字边讲、截屏操作指令等，若摘句无法证明**损害理解或合格线**，默认只进水平线或不写，**不得**进入 Top3 / 合格线。
10. **证据边界**：专业与结构判断默认仅基于转写 + 标题锚点；**公屏画面**（PPT / 笔记软件 / IDE 等）、未截到的后半课、真实师生话轮等，写入「待回放确认」，不强行定论。本仓适用场景**默认不使用黑板板书**；建议与改法中禁止默认「板书一下」，应写「在公屏 PPT / 笔记 / IDE 中演示」。
11. **授课力呈现裁剪**：上游授课力仍为六维；本步 `coach.md` / `report.md` **只展开 V1–V4**。V5 教学力、V6 数字力固定一句「本步不展开（非本版门禁）」，不写空转的「转写未体现」凑数。这是**报告呈现裁剪**，不是另立四维考核制度。

## 2. 流水线与产物（单视频）

| 顺序 | 步骤                         | 主要产物                                          |
| ---- | ---------------------------- | ------------------------------------------------- |
| 1    | 抽轨 / 转写 / 纠错           | `transcript_corrected.md`                         |
| 2    | **Pass A 专业预审**          | `knowledge_review.json`                           |
| 3    | 结构（总分总、小闭环与递进） | `structure.md`                                    |
| 4    | **讲解重点提纲**             | `teaching_outline.md`（须回避 Pass A issue）      |
| 5    | Pass B 综合建议与成稿        | `coach.md`（短稿）、`suggestions.md`、`report.md` |

Pass B **必须消费** Pass A JSON；不得无视闸门另起专业指控。  
纠错稿进入 Pass A/B / 提纲前，应去掉「以下为纠错说明」类**元前言**（实现层职责）。  
`lesson_type`：`principle` \| `code` \| `lab`（原理 / 代码 / 实操）；可由 `--lesson-type` 指定，否则按文件名启发式推断，写入 `manifest.json`（`lesson_type` + `lesson_type_source`）。  
**`coach.md` 面向老师**：只含结论摘要、Top3、教学能力四维；**合格线/水平线与待回放**写入 `suggestions.md` 并仅并入 `report.md`，以降低发给老师时的压力与篇幅。

## 3. `knowledge_review.json`（Pass A 契约）

### 3.1 顶层字段

| 字段              | 说明                                                    |
| ----------------- | ------------------------------------------------------- |
| `schema_version`  | 如 `1`（类别枚举可加法扩展，不必因 `clarity` 强升版本） |
| `title_anchor`    | 所用标题锚点（通常来自文件名 stem）                     |
| `anchor_strength` | `strong` \| `weak`（标题过泛时为 weak，结论须更保守）   |
| `summary`         | 2～4 句专业预审摘要（对事不对人）；**须遵守 §3.4**      |
| `findings`        | 数组，见下表                                            |

### 3.2 `findings[]` 元素

| 字段          | 说明                                                                                  |
| ------------- | ------------------------------------------------------------------------------------- |
| `id`          | 稳定短 id（如 `k1`）                                                                  |
| `category`    | `accuracy` \| `clarity` \| `case` \| `coverage_gap`                                   |
| `claim`       | 一句话判断（事实与评价分开语气）                                                      |
| `evidence`    | 纠错稿摘句；可含 `approx_time`；**无摘句则不得为 issue**                              |
| `verdict`     | `pass` \| `issue` \| `unverified`                                                     |
| `confidence`  | `high` \| `low`                                                                       |
| `remediation` | 可选改法（issue 建议有；unverified 可写「对照讲义或公屏回放确认」；禁止默认「板书」） |

### 3.3 类别含义与分工

| category       | 含义                                                                                       | 默认可进合格线 / Top3？     |
| -------------- | ------------------------------------------------------------------------------------------ | --------------------------- |
| `accuracy`     | 稿内明确表述与学科常识冲突（硬伤）                                                         | 仅 `issue`+`high`+有摘句    |
| `clarity`      | 标题锚点承诺的**核心关系 / 机制**在稿中**未可操作地讲清**（讲了字面/类比，但关系或用法虚） | 仅 `issue`+`high`+有摘句    |
| `case`         | 案例与主题严重错位或误导                                                                   | 仅 `issue`+`high`+有摘句    |
| `coverage_gap` | 标题暗示、转写中**整块未出现**（可能在未截取的后半课 / 下一节）                            | **否**（默认 `unverified`） |

**`clarity` 与 `coverage_gap` 的区分（必守）**

| 情形                                                          | 归类           | 说明                   |
| ------------------------------------------------------------- | -------------- | ---------------------- |
| 标题/开场承诺了某块，稿中完全未出现                           | `coverage_gap` | 待核实，不进必改       |
| 本段已声称「如何实现 / 理解 QKV」等，但机制未落地；有摘句可证 | `clarity`      | 可 `issue`（仍须摘句） |
| 仅因百科「还应讲 softmax」而指控，稿未声称该目标              | **禁止**       | 假阳性                 |

**机制线索（主题相关时的自检，非百科扩罪）**：当标题锚点明显指向「注意力 / QKV」等可核对机制时，Pass A 应自检稿中是否出现「匹配 / 相似度 / 分数 / 权重 / 加权」等**之一**作为可操作线索。若全无，且稿内有「实现 / QKV 含义」等口头承诺或小结声称已讲清，应产出 `clarity`（有摘句可 `issue`；拿不准则 `unverified`），**禁止**在 summary 写「讲解清晰」。

### 3.4 `summary` 约束

1. 必须与 findings 中**最高严重度**同向：存在 `issue` 或明确缺口时，不得写「整体清晰 / 案例恰当 / 讲解到位」类褒奖。
2. `findings` 为空，或**仅有** `coverage_gap` / 全为 `unverified` 时：用中性描述范围与边界；**禁止**无依据褒奖。
3. `anchor_strength=weak` 时：摘要更保守，少下结论性褒贬。

### 3.5 闸门（实现必守）

| 规则                            | 行为                                                      |
| ------------------------------- | --------------------------------------------------------- |
| 无 `evidence` 摘句              | 禁止 `verdict=issue`                                      |
| `coverage_gap`                  | 默认 `verdict=unverified`，不进合格线 / Top3              |
| `clarity` / `accuracy` / `case` | 有摘句且关系可核对手，允许 `issue`；拿不准用 `unverified` |
| 进入合格线 / Top3               | 仅 `verdict=issue` **且** `confidence=high` **且** 有摘句 |
| `unverified` / `low`            | 只进报告「待核实」或水平线旁注                            |
| Pass B                          | 不得新增无 Pass A 支撑的 knowledge / clarity `issue`      |

## 4. 单视频报告结构（`report.md`）

```markdown
# 课评报告 · 单视频

## 元信息

- 输入文件：
- 标题锚点：
- 课型：`principle|code|lab`（来源：cli|inferred）
- 运行 ID：
- 生成时间：
- 说明：专业判断仅基于转写与标题锚点，不是对照完整讲义的判分；公屏画面与未入稿内容见「待回放确认」（本仓默认非黑板板书）；授课力本步仅展开 V1–V4；讲解提纲为参考，非标准讲义。

## 结论摘要

（3～6 句：专业预审要点、讲清度、结构是否闭合、Top1 优先改进）

## 优先改进 Top 3

| 排序 | 类型 | 问题 | 证据摘句 | 改法 |
| ---- | ---- | ---- | -------- | ---- |

（选题权重：准确性 > 讲清度 ≥ 案例 > 结构/递进 > 表达/沟通；不足 3 条可不凑数。
若 Top3 全为结构/沟通，须有一句说明：「Pass A 未给出高置信知识/讲清度 issue；本表侧重结构/沟通。」）

## 专业预审（知识、讲清度与案例）

### 知识准确性

（汇总 Pass A 中 category=accuracy 的 findings）

（汇总 Pass A 中 category=clarity 的 findings）

### 案例恰当性

（汇总 Pass A 中 category=case 的 findings）

### 待核实

（unverified / coverage_gap / low confidence；默认不要求当次必须改）

## 课程结构与要点

### 总—分—总自检

- 开场总：
- 分述要点：
- 结尾总：
- 明显缺口：

### 小闭环与递进

- 各段小闭环是否清楚：
- 递进关系：
- 缺口：

## 教学能力摘要（授课力 · 本步展开 V1–V4）

- V1 专业力：（知识准确性、案例合理与适配；必须对齐 Pass A，不得另起专业结论）
- V2 设计力：（各小闭环是否闭合；小闭环之间衔接是否自洽）
- V3 表达力：（是否清晰、结构化）
- V4 沟通力：（是否有提问 / 设问；提问须具体、不空泛；无证据写「转写未体现」）
- V5 / V6：本步不展开（非本版门禁）

（不打考核分、不做否决语气。）

## 提升建议

### 合格线（必须改）

| 问题 | 证据摘句 | 改法 |
| ---- | -------- | ---- |

### 水平线（可选优化）

| 建议 | 证据摘句 | 改法 |
| ---- | -------- | ---- |

## 待回放确认（转写无法判定）

| 项  | 为何无法仅凭稿判断 | 建议回放关注点 |
| --- | ------------------ | -------------- |

（公屏上是否写出公式/示意图、是否切换到 IDE 演示、是否另有后续视频、学生真实回答等；无则写「本段转写范围内暂无」。**禁止**默认假设存在黑板板书。）

## 附录

- 教练短稿（可发老师）：`coach.md`
- 合格线/待回放：`suggestions.md`
- 结构要点：`structure.md`
- 讲解重点提纲：`teaching_outline.md`
- 纠错逐字稿：`transcript_corrected.md`
- 专业预审：`knowledge_review.json`
```

**`report.md` 组装原则（v0.6）**

1. 元信息（含课型）→ 嵌入 **`coach.md` 短稿** → 嵌入 **`suggestions.md`（提升建议 + 待回放）** → 专业预审（渲染器）→ `structure.md` → 讲解重点提纲 → 附录。
2. 不在报告里再抄一份与 coach 冲突的专业结论；Pass A 细节以渲染区块为准。
3. 结构细节以 `structure.md` 为准；coach 只引用结构结论，不重复粘贴整份结构稿进「教学能力」段。
4. 提纲须回避 Pass A `issue`，并标注「参考提纲，非标准讲义」。

### 4.1 `coach.md`（发给老师的短稿）

`coach.md` **只含**：

1. 结论摘要
2. 优先改进 Top 3（遵守 §1 权重与表达噪声闸门）
3. 教学能力摘要（**仅展开 V1–V4**；V5/V6 写「本步不展开」）

### 4.2 `suggestions.md`（仅进报告）

1. 提升建议（合格线 / 水平线）
2. **待回放确认**

专业 / 讲清度 / 案例的「必改」项**只能**来自 Pass A 中 `verdict=issue` 且 `confidence=high` 且有摘句的条目。Pass B 一次 LLM 调用产出五节，落盘时拆成 `coach.md` + `suggestions.md`。

## 6. 验收检查表（维护者试用）

- [ ] 结论摘要是否可在 30 秒内读懂？
- [ ] Top 3 是否遵守权重（准确性 > 讲清度 ≥ 案例 > 结构 > 表达），且无「无摘句却必改」的知识 / 讲清度 / 案例项？
- [ ] 是否出现「本段教学目标未讲清」却被「课表后半截未上」压过的错位？
- [ ] 「待核实」与「待回放确认」是否与合格线分开？
- [ ] 合格线与水平线是否混淆？口头禅等表达噪声是否误进 Top3？
- [ ] Pass A `summary` 是否在仅有 coverage_gap / 空 findings 时仍过度褒奖？
- [ ] 术语纠错是否忠实原意（随机抽 3 处对照 raw / corrected）？
- [ ] 全文是否避免指名批评教师、校区负责人或学员？
- [ ] 是否误把标题当完整讲义标准或用百科清单扩大指控？
- [ ] V1 摘要是否与 Pass A 同向？教学能力是否只展开 V1–V4，且 V5/V6 为「本步不展开」？

## 9. 讲解重点提纲与课型（已实现）

1. **`teaching_outline.md`**：在 `structure.md` 之后、`coach.md` 之前生成；偏**讲解重点提纲**；**必须回避** Pass A 中 `issue`+`high`+有摘句的条目；标注「参考提纲，非标准讲义」。
2. **`lesson_type`**：`principle` \| `code` \| `lab`；CLI `--lesson-type` 可覆盖；否则按文件名启发式推断；写入 manifest 的 `lesson_type` / `lesson_type_source`（`cli` \| `inferred`）。课型差异化提示词可后续加强，本版先预留字段并按课型给出公屏演示提示。
